# Research: Actual Parity

Phase 0 output for [plan.md](plan.md). Each entry is Decision / Rationale / Alternatives. "Actual" means `@actual-app/core` 26.8.1, the version `ActualMonthMath` is already pinned to. Where an entry names an Actual function, the port reads that function's source and the golden fixture (R1) decides any doubt.

## R1. How "matches desktop Actual" is proven

- **Decision**: Commit golden fixtures under `core/budget/src/test/resources/parity/`. Each fixture is a small Actual budget zip (spec 009 export shape) plus a script of actions and the rows desktop Actual 26.8.1 produced after each action (`zero_budgets`, `accounts`, `transactions`, `rules`, `schedules*`, `notes`, report totals). Fixtures are generated once with a small Node script against `@actual-app/api` at that version, checked in, and never regenerated by CI. JVM tests open the fixture on the phone side, run the same action through the book, and diff the resulting rows.
- **Rationale**: Every success criterion says "matches desktop Actual". A row diff catches drift that a total would hide (for example a copy that also wrote income categories).
- **Alternatives**: Hand-computed expectations (slow, and they encode our reading of Actual, not Actual). Running Node in CI (adds a toolchain to an Android build).

## R2. One write funnel for everything

- **Decision**: Every write in this spec calls `SyncSchema.recordLocal`. Its column map gains Actual's synced columns for `rules` (`stage`, `conditions_op`, `conditions`, `actions`, `tombstone`), `schedules` (`name`, `rule`, `active`, `completed`, `posts_transaction`, `tombstone`), `schedules_next_date` (`schedule_id`, `local_next_date`, `local_next_date_ts`, `base_next_date`, `base_next_date_ts`, `tombstone`), `notes` (`note`), `banks` (`bank_id`, `name`, `tombstone`), the bank columns on `accounts`, `categories.goal_def`, and `goal` / `long_goal` on both budget tables. `RulesBook.insertRule`, `SchedulesBook` writes, and spec 005's learning-rule inserts move onto the funnel. On the first open after upgrade, a backfill emits pending messages for any `rules` / `schedules` / `schedules_next_date` row that has no message in `messages`, so rules a phone made before this spec reach the server.
- **Rationale**: Today rules and schedules created on the phone never sync, which breaks Principle III. A single funnel is also what makes undo (R13) a small feature instead of one per screen.
- **Alternatives**: Per-feature sync code (duplicates `recordLocal`). Leaving old rows unsynced (desktop never sees them).

## R3. To-budget breakdown

- **Decision**: The envelope loop in `ActualMonthMath.envelopeDetailed` already computes `incomeSum`, `fromLast` (last to-budget + last buffered), `lastOver` (uncovered overspend from last month, ≤ 0), `budgetedSum`, and `buffered` for each month. Capture them for the target month into a `MonthBreakdown` on `DetailedFigures`. The breakdown screen shows them in Actual's order: Available funds (income + carried in), Overspent in last month, Budgeted, For next month, To budget. Tracking files show Actual's tracking summary instead (income budgeted vs received, expenses budgeted vs spent); there is no to-budget figure to break down.
- **Rationale**: FR-001 requires the parts to add up. Reading them from the same loop that produces the header makes that true by construction.
- **Alternatives**: A second query that re-derives the parts (can disagree with the header after a rounding or ordering change).

## R4. Copy last month, three-month average, set to zero

- **Decision**: Port Actual's `copyPreviousMonth`, `set3MonthAvg`, and `setZero` into `MonthFillBook`. Copy writes `budgeted(month-1)` for each visible expense category (hidden categories and categories in hidden groups skipped); on envelope files income categories are skipped, on tracking files income categories are copied as Actual does. Average uses the months among the previous three that have any budget row, rounding to the currency's minor unit the way Actual's `Math.round` does. Zero writes 0 for every category in the month. All three show a confirm when any visible category this month is already non-zero; until confirmed nothing is written. When the source months have no budget rows, copy and average report "nothing to copy" and write nothing. Each action is one journal step.
- **Rationale**: FR-002 and the edge cases. One step means one undo puts the whole month back.
- **Alternatives**: Per-category undo steps (one undo would only revert one category).

## R5. Transfer to to-budget

- **Decision**: Envelope only. Lowers the category's budgeted amount for this month by the transfer, which raises to-budget by the same amount, exactly as Actual's "Transfer to: To Budget" does. Refused when the amount exceeds the category's available amount. Optimistic update in `OpenMonthStore` before the write.
- **Rationale**: FR-003. Actual has no separate "transfer" record; it is a budget change.
- **Alternatives**: A negative hold (wrong table, desktop would show it as held).

## R6. Automatic hold for income

- **Decision**: In Actual, an income category's `carryover` flag on a month means "hold this income for next month" and feeds the sheet's `buffered-auto`. `ActualMonthMath` already reads it. Turning auto-hold on writes `carryover = 1` on the income category's budget row for this month and the following 12; turning it off for this month writes `carryover = 0` on this month only; turning it off entirely writes 0 for this month and the following 12. A manual hold (`zero_budget_months.buffered`) still overrides auto for that month, matching the sheet.
- **Rationale**: FR-004 and acceptance 7–8. Reuses the existing math and table.
- **Alternatives**: A phone-only preference (desktop would not see it).

## R7. Accounts

- **Decision**: Port `account/create`: an `accounts` row (`name`, `offbudget`, `sort_order` after the last), a transfer payee for it, and when the balance is non-zero a Starting Balance transaction dated today with the "Starting Balance" payee and, on budget, the income category Actual uses for starting balances (created if absent, same name and group as Actual). Notes write `notes` row `account-<id>`. Reorder writes `sort_order` midpoints like Actual's `shoveSortOrders`. Close ports `account/close`: zero balance closes directly; otherwise a transfer transaction to the chosen account dated today, with a category required when the money moves from on-budget to off-budget. Force close ports the forced branch: transfer partners are unlinked and re-payeed, then the account and its transactions are tombstoned, so the month drops that money. Reopen writes `closed = 0`. Closed accounts are filtered from the list unless "show closed" is on (a phone preference in `phone.json`, like Actual's UI toggle).
- **Rationale**: FR-005 and FR-006. Force close's effect on the month (acceptance 5) follows from tombstoning.
- **Alternatives**: Force close that only sets `closed = 1` (month would not change; does not match Actual).

## R8. Schedule editor and auto-post

- **Decision**: The editor builds the same rule + schedule pair Actual's schedule editor does: a `rules` row with conditions on `description` (payee), `acct`, `amount` (`is`, `isapprox`, `isbetween`), and `date` (a recur config: `frequency` daily/weekly/monthly/yearly, `interval`, `start`, `endMode` never/after_n_occurrences/on_date, `endOccurrences`, `endDate`), a `link-schedule` action, and optionally a category action. One-time schedules use a plain date value. Patterns and `skipWeekend` in an existing config are kept and still evaluated by `ScheduleRecurrence` but are not editable. Auto-post (`posts_transaction = 1`) runs in `SyncCoordinator` after the budget opens and after each sync: for each due occurrence it uses spec 005's match rule; with a match it advances only, otherwise it posts and advances, in one journal step. It runs only while the app is open; a later open posts the occurrence that came due and does not stack duplicates.
- **Rationale**: FR-007, FR-008, SC-003. Spec 005 already owns posting and the near-duplicate rule; this reuses both.
- **Alternatives**: WorkManager background posting (spec says it does nothing while the app is closed, and it would write while the screen is not reading).

## R9. Rule editor, unknown parts, and speed

- **Decision**: The editor model has typed rows for the six condition fields (payee, account, category, amount, date, notes) with Actual's ops for each, and six action fields (payee, category, notes, amount, date, cleared) with `set` (plus `prepend-notes` / `append-notes` for notes). Stage is pre / default / post. Any condition, op, or action the model does not recognise (for example `imported_payee`, `hasTags`, `set-split-amount`, `delete-transaction`) is held as raw JSON, shown as "kept from the file", and written back unchanged. `RuleEngine` evaluates every op Actual supports for the fields it reads; an op it cannot evaluate makes the rule not match, never crash. Rules are parsed and ranked once per budget open and cached; a rule write invalidates the cache. Delete writes `tombstone = 1`. Disable keeps today's `disabledRules` preference.
- **Rationale**: FR-009, FR-010, SC-004. Raw passthrough is what keeps a desktop-built rule intact.
- **Alternatives**: Dropping unknown parts on save (fails FR-010). Re-parsing all rules each save (fails SC-004 at 100 rules).

## R10. Category learning

- **Decision**: Read and write Actual's synced preference `learn-categories` (absent = on). When on, after a transaction save that sets a category for a payee, run a port of Actual's `updateCategoryRules`: find or create the default-stage rule whose single condition is `payee is X` and whose action sets category, and point it at the category Actual would choose. When off, skip that call; existing rules still run.
- **Rationale**: FR-011 and acceptance 5. Using Actual's preference id means desktop and phone agree on whether learning is on.
- **Alternatives**: A phone-only switch (desktop would keep learning from the same file).

## R11. Reports

- **Decision**: `ReportsReader` runs three read-only queries over living transactions (`tombstone = 0`, parents excluded when children exist, as `v_transactions_internal_alive` does):
  - **Cash flow**: income = sum of positive amounts, expenses = sum of negative amounts, on-budget accounts, transfers between on-budget accounts excluded, grouped by month for the range. Totals and difference.
  - **Net worth**: balance of each account at the end of each month in the range (running sum up to that date), summed; off-budget accounts follow spec 006's include choice.
  - **Spending**: expenses only (negative, on-budget, not a transfer), grouped by category, group, or payee, largest first.
  Range picker presets plus a custom start/end month. Empty range = zero rows and zero totals.
- **Rationale**: FR-012 and SC-005. These are the definitions desktop Actual's cash flow, net worth, and spending reports use; fixtures confirm.
- **Alternatives**: The custom report builder (FR-018 excludes it).

## R12. Budget templates

- **Decision**: Gate: on only when `flags.experimental` (spec 009's switch) and `flags.goalTemplatesEnabled` (Actual's own flag id) are both `true`; settings shows the second switch under the first. Notes are always editable (`notes` row = category id). `TemplateParser` reads lines beginning `#template`, `#template-N` (priority N), and `#goal`, covering: fixed amount, `up to` limit, `by <month>` with `repeat every N months/years`, `schedule <name>` (with `full`), percentage `N% of <category|all income|available funds>` (with `previous`), `average N months`, `remainder` with optional weight, and `#goal` amount. `TemplateEngine` ports the 26.8.1 engine: process priorities lowest number first, each priority limited by what to-budget has left, remainder last split by weight, hidden categories skipped. Check reports invalid lines by category name and writes nothing. Apply writes only categories whose budgeted amount is zero. Overwrite writes all templated categories after confirm. Each run writes `budgeted` plus `goal` / `long_goal` the way Actual does, as one journal step. `categories.goal_def` is written with Actual's parsed form so desktop sees the same stored templates.
- **Rationale**: FR-013, SC-006. Two flags match Actual's feature-flag model while keeping spec 009's single experimental umbrella.
- **Alternatives**: A parser generator (adds a build dependency for one grammar). Applying templates whenever experimental is on (desktop would disagree when its flag is off).

## R13. Undo

- **Decision**: `EditJournal` keeps a stack of steps for the open budget in memory. `EditJournal.step { }` opens a step; `recordLocal` inside it reads each cell's current value before writing and appends `(dataset, row, column, old, new)`. Undo pops the newest step and, for each cell in reverse order, first checks the cell still holds `new`. If all match, it writes `old` through `recordLocal` as new pending messages (new HLC timestamps, so the server takes them like any edit). If any cell was changed by a remote message since, nothing is written and a conflict is added to spec 004's conflict list naming the cell, the value before the person's edit, and the server's value. The stack is cleared on budget switch, on app process death, and is capped at 100 steps. Bank fetches and auto-post steps are journaled too, so the person can undo a bad auto-post.
- **Rationale**: FR-015, SC-007, acceptance 6. Writing forward (not deleting messages) is how Actual's own undo works and keeps sync monotone.
- **Alternatives**: Deleting the pending message (fails once it has been sent). A persisted journal (spec limits undo to this session).

## R14. Bank links

- **Decision**: Use the active instance's server provider endpoints, as desktop Actual does: `GET .../{provider}/status`, then per provider: GoCardless `create-web-token` (open the requisition link in a Custom Tab, then poll `get-accounts` for the requisition), SimpleFIN `POST /secret` with name `simplefin_token` (the setup token; the field is cleared after posting and never shown again) then `simplefin/accounts`, Pluggy.ai `pluggyai/accounts` after its server-side secret is set the same way. The person matches one external account to the phone account. Link writes a `banks` row and `accounts.account_id`, `bank`, `account_sync_source`, balances, and clears `last_sync`. Replace = link again over the same account. Remove = clear those columns, the way `account/unlink` does; fetch is then no longer offered (spec 007 already hides fetch when `account_id` is blank). Unreachable provider shows an inline error; the budget stays usable.
- **Rationale**: FR-014 and the "no new provider" assumption. Secrets live only on the server.
- **Alternatives**: Talking to providers directly from the phone (Actual does not; would need provider keys on the phone).

## R15. Tracking files

- **Decision**: Month fills, templates, and undo write `reflect_budgets` on tracking files, following Actual's tracking rules (no to-budget, no hold, no transfer to to-budget, income categories budgeted). Breakdown, transfer to to-budget, and auto-hold are absent on tracking files. No action writes `budgetType`.
- **Rationale**: FR-017, Principle III.
- **Alternatives**: Hiding every month action on tracking files (they exist in Actual for tracking too).
