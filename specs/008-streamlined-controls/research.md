# Research: Streamlined Metro Controls

Phase 0 output for [plan.md](plan.md). Each entry is Decision / Rationale / Alternatives.

## R1. One open month

- **Decision**: `ShellUiState` keeps a single `openMonth: YearMonth`. The budget section and the month review both load that month. `budgetMonth` and `reviewMonth` go away. Routes that edit a category for a month (`GroupCategories`, `CategoryBudget`, `MoveCategory`, `HoldMonth`) store `pinnedMonth` when they are pushed. Their reads and writes use `pinnedMonth` until the route is popped. `openMonth` can change while that route is still showing. Popping back shows whatever `openMonth` is now. `ManageCategories` is not month-scoped and does not pin a month.
- **Rationale**: The spec requires one panorama month for the budget and the review, and it requires a category editor opened on October to stay on October after the panorama month changes. Two fields that are copied on every tap can drift. Pinning on the route is the month the editor was opened on.
- **Alternatives**: Keep both fields and assign them together (the review button can still move one of them). Freeze `openMonth` while an editor is open (the person cannot change the panorama month until they leave, which misses the edge case).

## R2. The month control and the in-memory window

- **Decision**: One `MonthControl` sits in the shell chrome, under the panorama title, on Home and on the four pinned editor routes. It is absent when no budget is open. It shows `monthLabel(openMonth)` (name and year). Icon actions: previous, next, and current calendar month. Previous is absent on the oldest month in the window. Next is absent on the newest. Current calendar month is absent when `openMonth` is already that month. Tapping the month name expands an in-place list of every month from 24 months before the current calendar month through 24 months after it (49 months). Choosing a row sets the month and collapses the list. The person does not get a new route. The word buttons for previous month, next month, hold, and manage leave `BudgetSection`. The review section's previous-month button leaves too.
- **Decision**: A `MonthCache` maps `YearMonth` to the `MonthShell` and `MonthReviewPage` already read for this budget. When a budget opens, and when the calendar month rolls, the app fills the 49-month window on `Dispatchers.IO`. A tap whose month is in the cache and whose list is not scrolling applies that snapshot in the same `MutableState` update as the tap. A tap during a list or panorama scroll stores the month and applies the snapshot when the gesture ends, reusing `RefreshGate`. A tap whose month is not cached yet still sets `openMonth` before the click handler returns, so the name changes immediately, and applies figures when the read returns. An empty month shows zeros and no error. The displayed budget name is one ellipsized line in its own slot, not on top of the control or the header amount.
- **Rationale**: Disk I/O on the tap path would violate Principle I, and waiting for I/O would miss "before the finger lifts" for previous and next. Those two, and a picked month inside a warm window, are cache hits. The window is bounded, so the warm is finite. The name does not wait on the cache, which covers the cold case without a spinner.
- **Alternatives**: Read sqlite inside the click on the main thread (jank, and it breaks the constitution). Keep previous and next as list buttons (the clunk the spec removes). A separate review month (spec 006's control; this spec replaces it). Persist `openMonth` in `phone.json` (the success criterion asks for figures after restart, and those already live in the file; the viewed month can return to the calendar month on a new process, which is what the app does today).

## R3. A bar that follows the screen

- **Decision**: `ScreenBar.forState` returns the primary actions and the secondary actions for the current route. `MetroAppBar` draws primary actions as 48 dp round outlined buttons, at least 8 dp apart, and draws secondary actions only in the menu the ellipsis opens. The ellipsis toggles that expansion. It does not navigate. Labels under the icons show only while expanded. A primary icon runs its action once whether or not the labels are showing. The clickable area is the circle, not the gap and not the neighbor's label. `AppGlyph.More` (an empty `when` branch) is removed. Every remaining glyph has a stroked canvas drawing: hold, categories, add, settings, transfer, reconcile, import, save, cancel, budgets, appearance, sync, payees. No glyph draws only an empty circle.
- **Decision**: Actions by screen, using the methods the app already has:
  - Home, budget open, envelope: primary add, hold, categories, settings. Secondary none.
  - Home, budget open, tracking: the same without hold.
  - Home, no budget: primary settings only.
  - Register: primary add, transfer, reconcile, import.
  - Write forms (create, assign, add transaction, edit, split, transfer, hold, category budget, move, import preview, reconcile, budget password): primary save and cancel. Save runs the write that screen already performs. Cancel pops and does not write. For reconcile, save finishes and cancel runs `cancelReconcile`. For import preview, save confirms and cancel runs `cancelImport`. For budget password, save unlocks and cancel leaves without writing the budget.
  - Every other route: no panorama actions. Confirmation routes keep their existing confirm and stay actions. Appearance, server, budgets, and payees stay as screens. They are not icons on the panorama.
- **Decision**: Settings is a new `ShellRoute.Settings` whose title is "settings". It lists the screens the panorama bar used to open: budgets, appearance, sync, and payees. That is the recognizable settings place until spec 009. This spec does not add instances or move file switching into a new model.
- **Rationale**: The bar is one list for every route today (`budgets`, `sync`, `payees`, `appearance`), and `More` draws nothing, which is why icons feel dead. Putting the actions on the route that owns them removes the word-button row and the dead icons together. Four 48 dp targets plus an ellipsis fit a 360 dp width when the gap is 8 dp. Spec 009 owns the real settings content, so this screen is only a door.
- **Alternatives**: Leave the global bar and add more icons (the empty-glyph problem gets worse). Hide primary actions until the ellipsis opens (the spec forbids that). Build spec 009's instance list here (out of scope).

## R4. Title lag

- **Decision**: Replace the gutter clamp and the 15% title-width travel as the thing a person sees. `PanoramaMotion.titleShiftPx` takes the unwrapped pager position, the section count, a step in pixels, and whether motion is enabled. When motion is off, or there is only one section, the shift is 0. Otherwise the resting shift is 0 on even pages and `-step` on odd pages, and a fractional page lerps between those. Adjacent pages, including the loop, always differ by `step`. `step` is the measured width of the word "due" in the subtitle style. The title's rest inset is at least that step, and the title block scales down from 118 sp only when `inset + block width` would pass the viewport. `clip` stays off on the title. The parent no longer does `coerceIn(-gutter, 0)`. A single section disables sideways scrolling. Peek and snap stay on `HorizontalPager`.
- **Rationale**: The current shift is 15% of the title width and is then clamped to the 12 dp gutter, so the lag is a few dp and can clip. A continuous per-section offset of at least one "due" across all six sections cannot fit an oversized "budget" on a phone. Alternating by page parity keeps every swipe's travel equal to that word and keeps the maximum translation inside one step, so the title stays on screen. Reduced motion is a zero shift, not a jump to the other parity.
- **Alternatives**: Keep 15% and drop the clamp (the title leaves the screen). Shrink the title so five steps of travel fit (it stops being the Metro title). Move the title only while the finger is down and always rest at 0 (the end of the swipe is a jump back, which the spec forbids).

## R5. What this spec does not change

- **Decision**: No new tables, columns, or preferences. Hold, manage, add, transfer, reconcile, import, and save call the existing ViewModel methods. Sync still runs in the background and still loses to a gesture that is in progress. The network permission stays unused by these controls.
- **Rationale**: FR-014. The work is how the person reaches actions, not a second set of numbers.
- **Alternatives**: Recompute to-budget in the control (a parallel total). Prefetch through the Actual server (breaks offline).
